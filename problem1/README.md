# 单日 10,000+ 任务导致业务主库和服务器过载的解决方案

本方案的首要目标是**在任务高峰期间保障在线业务可用，同时让已受理的任务在约定时限内完成**。落地顺序是先定位瓶颈、限制批任务占用的资源，再通过错峰调度、消息队列和数据库优化提高处理能力，并建立过载时自动降速、恢复后逐步提速的机制。

## 一、问题定位

单日 10,000 个任务平均约每 8.6 秒到达一个。若这 10,000 个任务集中在 5 分钟内触发，到达率约为每秒 33 个。两者的日任务量相同，后一种情况下这 5 分钟的平均到达率约为全天均匀到达时的 288 倍。因此，首先要确定**任务何时集中、每个任务消耗多少资源，以及在线请求具体卡在哪里**。

选取一次业务变慢的时间窗口，对照以下数据，并与正常时段比较。

| 排查层面 | 采集的关键指标 | 要回答的问题 |
|---|---|---|
| 在线业务 | 核心接口 P99 响应时间、超时率、错误率 | 哪些用户操作最先变慢？是否与某类任务启动重合？ |
| 任务执行 | 每分钟到达数、完成数、运行中任务数、执行耗时、重试次数 | 是集中触发、单任务变慢，还是失败重试增加了实际工作量？ |
| 应用服务器与任务进程 | CPU、在途请求数、线程池排队时间、数据库连接获取耗时、单个任务进程的内存峰值；JVM 另看堆内存使用率、Full GC 次数和 GC 停顿时间 | 线程在等连接，还是单个大任务拉高了堆占用？GC 停顿是否与任务吞吐下降同时发生？ |
| 业务主库 | 慢 SQL、扫描行数、活跃连接、锁等待、磁盘 I/O、读写比例 | 压力主要来自重复读取、低效查询、集中写入，还是热点行竞争？ |

排查时，选取一个受影响的在线请求和一个同期运行的批任务，分别追踪到具体 SQL。例如，如果在线请求的大部分时间消耗在获取连接，而任务线程又因一条慢 SQL 长期占用连接，就应同时处理消费并发和这条 SQL。单纯调大连接池，可能让更多慢查询同时进入主库。

## 二、原因分析

根据题目，优先验证以下三类原因，最终以监控和调用链结果确定。

1. **任务到达速度短时超过处理速度。** 定时任务整点触发，或上游一次提交大批任务。如果执行端收到任务后立即并行处理，瞬时压力就会直接传到服务器和数据库。
2. **单个任务的数据库开销过高。** 例如循环逐条查库、反复读取同一份配置、查询缺少合适索引，或者多个任务同时更新同一行汇总记录。这些问题会拉长执行时间，使更多任务同时占用连接。
3. **批任务与在线请求共享资源，过载后仍持续接收工作。** 批任务耗尽线程、连接或数据库 I/O 后，用户请求开始排队。若超时任务立即重试，旧任务尚未结束，新一轮请求又进入系统，局部变慢就可能扩大为服务不可用。

## 三、解决方案

### 1. 先隔离资源，给在线业务保留处理能力

将批任务放到独立的工作进程中执行，为其配置独立的线程池和数据库连接池。在线服务保留自己的连接预算。若排查确认批任务会耗尽同机 CPU 或内存，再为工作进程设置资源限额，或部署到独立节点。

**消费并发和数据库连接预算要按所有实例合计。** 例如一个工作进程最多使用 10 个数据库连接，部署 10 个实例后，批任务就可能同时占用 100 个连接。应在模拟正常在线流量的压测中，逐步提高批任务并发，找到核心接口仍能满足响应目标的范围，并留出波动余量。

对于已有的整点任务，可以先做低成本止压：把允许延迟的任务分散到多个时间窗口，限制每批启动数量，并让低优先级报表、统计任务避开业务高峰。

### 2. 用消息队列削峰，按下游承载能力消费

对允许异步完成的任务，采用事务型 Outbox，按以下顺序处理。

1. **受理。** 接口在同一数据库的一个本地事务中写入任务记录和 `outbox` 待投递记录。事件带有唯一事件 ID 和任务 ID。事务提交后即可返回任务 ID，调用方据此查询进度。
2. **投递。** 独立投递器按状态和下次投递时间分批领取到期记录。领取使用有过期时间的租约，释放数据库事务后再发送消息。收到消息队列的持久化确认后标记已发送。进程在发送前退出，租约到期后可重新领取；在队列确认后、标记前退出，同一事件可能再次投递。
3. **执行。** 消费者在分配的并发预算内领取任务，记录有时限的执行租约。进程退出且租约过期后，其他消费者可接管未完成任务。提交结果时校验租约版本和业务幂等键，防止过期执行者覆盖接管者的结果。结果提交后再确认原消息。分别监控最老待投递记录和最老待消费消息的年龄，以区分积压发生在哪一段。

消费端还要处理三个实际问题。

- **重复投递。** 使用任务 ID 或业务唯一键做幂等控制。对于库内更新，将幂等记录与业务结果放在同一事务中。这样即使消费者在提交结果后、确认消息前退出，重复消费也不会再次产生同一笔业务变更。
- **分层重试。** 对可恢复的瞬时故障，先在进程内快速重试 1～2 次；仍然失败就释放工作线程，通过延迟队列稍后执行。例如按 10 秒、1 分钟、5 分钟、30 分钟逐级退避并加入随机抖动，根据任务截止时间裁剪档位。每次尝试前在任务记录中原子领取并计入次数，快速与延迟重试共用总预算。安排延迟重试时，把下一次尝试的序号、到期时间和待投递事件在同一事务内持久化，再确认原消息。消费者重启后按已存状态继续，重复到达的旧序号直接跳过。参数错误直接记为失败，预算耗尽或超过截止时间则记录终态并转入死信处理。
- **积压超时。** 同时监控队列长度、最老任务等待时间和任务完成速率。如果主库尚有余量，可以提高消费并发。如果主库已经接近安全上限，就延后低优先级任务，必要时在受理新任务前明确返回限流结果。

**用任务时限校验队列方案是否可行。** 假设高峰一次到达 10,000 个任务，要求 30 分钟内全部完成，且期间没有新增任务，那么系统平均至少要完成约 5.6 个任务/秒。如果保障在线业务时实测只能稳定完成 4 个/秒，清空这批任务至少需要约 42 分钟。此时必须降低单任务成本、提前错峰或扩充实际瓶颈资源，单靠排队无法满足时限。

### 3. 控制单个批任务的内存

一个任务需要遍历数万条明细时，写入端每批只提交几百条，也可能在读取阶段就耗尽内存。应同时限制每次读取的数据量和等待处理的数据量。

- **流式读取。** 使用驱动支持的服务端游标逐批拉取，例如使用 MyBatis Cursor 时，核实 JDBC 驱动的抓取设置确实生效。若处理慢、长期占用游标连接会挤压连接池，可按有索引的稳定键分页，每页处理后再取下一页。
- **有界队列背压。** 读写并行时，在读取端和处理端之间放置有容量上限的阻塞队列。队列满即暂停读取，腾出空间后继续。按单条记录大小、并行任务数和可用堆内存确定容量，同时计入驱动预取和写入批次。串行任务可以直接采用“读一批、处理一批、再读下一批”。
- **分批恢复。** 需要断点续跑时，将批次结果与已完成位置一起提交。并行处理按已连续完成的位置推进检查点，重放时按明细业务键去重，避免跳过尚未完成的批次。

### 4. 根据瓶颈选择数据库和缓存方案

| 实际观察到的瓶颈 | 解决方法 | 实施要点 |
|---|---|---|
| 慢 SQL、逐条读写或长事务 | 优先优化 SQL、索引和批处理 | 根据执行计划调整索引，将循环查库改为批量查询。大事务拆成有界的小批次，在业务允许的边界提交，缩短持锁时间 |
| 大量任务反复读取相同数据 | 使用 Redis 缓存热点数据 | 优先缓存配置、字典等高频读取且允许短暂延迟的数据。设置过期与更新策略，同一热点失效时合并回源请求，并限制缓存异常时的回源并发 |
| 报表、历史查询等读取占主库负载的大头 | 采用读写分离 | 将可容忍复制延迟的查询路由到只读副本，监控复制延迟。需要立即读到最新写入结果的查询继续走主库 |
| 多个任务竞争更新同一条记录 | 减少热点写入和锁竞争 | 例如按业务允许的时间窗口先汇总增量，再合并更新，避免每条明细都争抢同一行 |
| 优化后仍存在持续的单库写入或容量瓶颈 | 评估分库分表 | 选择分布均匀、与常用查询匹配的分片键，先验证热点分片、跨分片查询和迁移成本。若瓶颈是实例总 I/O，仅在同一实例内拆表，收益有限 |

**写后读路由。** 任务状态刚更新，同一请求链路中依赖该更新的查询固定走主库。跨请求也要求读到本次写入时，可携带提交位点，确认副本已回放到该位点再读副本，否则走主库。普通展示查询若允许短暂旧值，可按观测到的复制延迟设置会话粘主窗口。复制延迟可能超过窗口，结算、状态迁移等关键判断始终使用能确认最新状态的数据源。

**Redis 异常防护。** 单个热点键过期时合并并发回源。对于反复查询的不存在 ID，仅在数据库明确返回“不存在”时缓存短期空值，例如 60 秒，并在创建对应记录后失效该空值。对批量预热的数据，在基础 TTL 上加入随机偏移，错开过期时间。整组缓存不可用时，继续用回源并发上限保护主库。

### 5. 建立自动保护和恢复机制

保护机制应在在线服务出现大面积超时前开始动作。用核心接口 P99、错误率、获取数据库连接的等待时间和主库负载共同判断压力。具体阈值、持续时间和恢复窗口通过业务目标与压测确定。

| 系统状态 | 触发信号 | 自动动作 |
|---|---|---|
| 正常 | 在线接口达标，数据库有余量 | 按基准并发消费，持续跟踪任务等待时间 |
| 压力升高 | 连接等待持续增长、在线接口延迟接近上限，或资源信号连续多个窗口恶化 | 分档降低消费并发，延迟启动低优先级任务 |
| 严重过载 | 核心接口持续超时，或数据库连接接近耗尽 | 暂停领取低优先级任务，限制新批量提交，告警并保留已受理任务。为正在执行的 SQL 和事务设置合理超时，防止连接长期占用 |
| 恢复 | 在线延迟和数据库指标在恢复阈值内持续稳定 | 先恢复少量消费，再逐级提速；每级观察在线延迟和连接等待，压力反弹时退回上一档 |

**资源信号可提前触发降速。** 按相近在线流量建立健康基线，观察 CPU、在途请求数和完成速率。若 CPU 持续高于安全水位、在途数上升而完成速率持平，可在 P99 超标前先降低一档批任务并发。若云盘 I/O 变慢，CPU 可能仍低，此时结合磁盘延迟、数据库等待和在途数判断。降速后观察是否改善，再决定下一档动作。

恢复阈值应比降速阈值留出余量，避免指标在临界点附近波动时频繁暂停和重启。**队列积压和主库过载同时出现时，以保护在线业务为先**，不能只看队列长度自动扩消费者。

## 四、实施顺序与验收

1. **先止压。** 补齐核心监控，限制现有任务并发，错开集中调度时间，优先对照慢 SQL 的执行计划和最大单任务的内存曲线，修复异常扫描或一次性全量加载。在相同输入规模下复测接口延迟、连接等待和单任务内存峰值。
2. **再改造任务链路。** 选取一类任务接入可靠队列和独立工作进程，小流量验证任务状态、幂等、重试、限流及恢复，再逐步扩大范围。
3. **最后按数据扩容。** 在相同在线流量和任务峰值下复测，根据剩余瓶颈决定是否引入 Redis、只读副本或分片。

验收前约定在线接口 P99、错误率、任务完成时限，以及批任务可用的连接和内存预算。在接近生产规模的测试环境保留正常在线流量，按下表演练。

| 场景 | 通过条件 |
|---|---|
| 集中提交一轮峰值任务，再逐步降低主库 I/O 能力并恢复 | 在线指标满足约定目标，消费端能按压力降档并逐步恢复；在约定的峰值和故障持续时间内，积压能按时清空 |
| 在任务事务提交后、队列确认后但标记前、业务结果提交后但消费确认前分别停止相应进程 | 重启后所有已受理任务都有可追踪的终态，同一业务结果只生效一次 |
| 让依赖持续失败，在延迟重试期间重启消费者 | 重试次数跨重启保持，达到预算或截止时间后进入死信处理，可按任务 ID 核对尝试记录 |
| 增大单任务明细量并放慢处理端 | 队列达到容量后读取暂停，堆内存峰值保持在预算内；恢复处理后，明细无遗漏或重复生效 |
| 在副本延迟超过粘主窗口时写入并立即查询 | 需要读到本次写入的操作仍返回已提交版本 |
| 重复查询不存在的 ID、批量预热键到期，以及 Redis 暂时不可用 | 空值缓存命中后减少重复查库，批量键分散过期；缓存不可用期间，回源并发仍在主库预算内 |
